## 1. 확정된 설계 결정 (근거 포함)

### 1-1. 검색은 "2-레인" 구조, 병합(融合) 안 함
분실물 조회 결과를 **두 개의 독립 레인으로 분리**해서 나란히 보여준다.

| 레인 | 방식 | 대상 | 성격 |
|------|------|------|------|
| 🔎 **특징으로 찾은 습득물** | 텍스트 하이브리드(BM25+임베딩) + 가점 | 거의 전체 습득물 | **주력** |
| 🖼 **사진이 비슷한 습득물** | 이미지 KNN 유사도 | 사진 있는 항목 한정(주로 포털기관) | **보조** |

- **근거**: 텍스트 점수와 이미지 유사도 점수는 스케일이 달라 RRF 같은 융합이 필요한데,
  레인을 나누면 그 복잡도 자체가 사라진다. 이미지 레인의 "반쪽 커버리지"도 결함이 아니라
  "사진 있는 것 대상"이라는 **명시된 성격**이 된다.
- 두 레인 사이 중복은 dedup 불필요(각자 표시, 필요 시 배지만).

### 1-2. 장소·시간·특징은 하드필터가 아니라 **가점(boosting)**
- **근거**: 습득물 텍스트가 빈약(브랜드·모델 미기재)하고 표기 불일치(검정 vs "블랙(검정)")가
  잦아, 조건을 AND 필터로 걸면 **정답이 탈락하고 결과가 0건**이 된다.
- 조건은 "정답을 좁히는 필터"가 아니라 "순위를 정하는 점수"로 쓴다. **Recall을 넓게** 가져가고
  **정밀도는 뒤에서 LLM grading**이 근거와 함께 정리.
- 유일하게 하드필터로 정당한 것은 **시간**(습득일 ≥ 분실일, 상한 오늘) 정도. 그것도 좁히지 않기.

### 1-3. 이미지 검색은 **모델 학습 불필요**, "특징 텍스트화"가 주력
- **A. 비전 LLM 특징추출(Gemini Vision)**: 사용자 사진 → 카테고리별 구조화 특징(휴대폰=모델/색/케이스,
  가방/의류=브랜드/색/소재) → **기존 텍스트 검색에 합류**. 습득물이 텍스트만 있어도 매칭돼 커버리지 유지. → **1순위**
- **B. 멀티모달 이미지 임베딩(CLIP/SigLIP/Gemini)**: 사진→벡터→이미지 KNN. 사진 있는 항목 한정. → **보조**
- 추출 특징에는 **신뢰도(confidence)**를 달아 boost 가중으로만 쓰고, 하드필터로 쓰지 않는다(환각 방어).

### 1-4. LLM은 "데이터베이스"가 아니라 "심판"
- 습득물 데이터는 **인터넷에 없고**(구글·LLM 학습데이터에 없음) 공공 API 뒤에 있음.
  10만 건을 프롬프트에 넣는 것도 불가(토큰·비용·환각).
- 구조: **검색 인덱스가 10만 건 → 후보 ~50건으로 싸게 좁히고, 그 50건만 LLM이 판정/설명.**
- LLM이 잘하는 것은 따로 활용: 인터넷 지식(모델 이미지 검색), 언어 이해("택시에 두고 내린"), 노선 추론.

### 1-5. 가점은 많다고 좋은 게 아니다 — **eval로 검증하며 추가**
- 데이터에 없는 필드에 건 가점은 신호가 아니라 소음. 가점을 쌓을수록 과적합·튜닝 지옥.
- **린 baseline(전국·텍스트+색 의미검색·가점 없음)부터 시작** → 가점 하나 추가 시 MRR/Recall이
  오르면 유지, 안 움직이면 버림. 조건의 많고 적음은 취향이 아니라 **측정 대상**.

  `depPlace`(보관장소)로 구분됨. **커버리지 완성을 위해 둘 다 수집.**

### 2-2. 엔드포인트 (base: `http://apis.data.go.kr/1320000`)

```
# 경찰청 습득물
GET /LosfundInfoInqireService/getLosfundInfoAccToClAreaPd   # 목록
GET /LosfundInfoInqireService/getLosfundDetailInfo          # 상세

# 포털기관 습득물 (스키마 동일, 오퍼레이션명만 다름)
```

- **serviceKey**: URL에는 "인코딩 키"를 사용(디코딩 키의 `+`→`%2B`, `/`→`%2F`, `=`→`%3D`)

## 4. AI 에이전트 매칭 흐름 (설계)

사용자: *"2250번 버스 타고 사가정역 가는 길에 버스에서 샤넬 검은색 지갑을 잃어버렸다. 모델은 000."*

```
1) LLM 추출  → {물품:지갑, 색:검정, 브랜드:샤넬, 모델:000,
                장소맥락:[2250버스, 사가정역], 분실일:...}
2) 질의 fan-out (하나의 정교한 쿼리 X → 넓게~좁게 여러 후보 쿼리)
     - 특징 레인: "샤넬 검정 지갑" / "검정 카드지갑" / "지갑"
     - 장소 가점: 2250 노선 경유 지역·버스회사 → 해당 depPlace/지역 boost (필터 X)
     - 시간: 분실일~오늘 (넓은 범위)
3) 이미지 레인: 샤넬 000 모델 웹검색→이미지 → 이미지 임베딩 → 유사 사진 KNN
4) LLM grading: 각 후보가 "샤넬 검정 지갑"에 맞는지 판정 + 근거 설명
```

- 서울 버스노선/위치 API(사용자 계정에 승인됨)로 노선→경유지 추출 = 실제 에이전트 강점 포인트.
- 모든 조건은 **가점**으로만. 데이터에 "샤넬"이 없을 수 있으므로 필터로 걸면 정답 탈락.

## 5. eval(성능 측정 장치)이란

- **골든셋**: 질의 + 정답(atcId)이 정해진 문제집. 예: `"택시에 두고 온 회색 여성 지갑" → F2026083100004003`
- **채점 스크립트**: 검색을 돌려 정답이 몇 위에 오는지 → **Recall@k, MRR**
- 알고리즘 변경 시마다 숫자로 좋아졌는지 판단(예: "가점 넣으니 MRR 0.4→0.6").
- **인프라·API 키 불필요** — 매칭 품질을 가장 싸고 빠르게 확인하는 방법. 여기서 나온 숫자가 하한선.

### 실험 계획 / 진행
1. 코퍼스 확보 — ✅ 완료 (2,000건, `eval/data/corpus.json`)
2. 골든셋 v0 — ✅ 완료 (`eval/golden/golden.json`, 12문항, 동의어 난도 케이스 포함)
3. BM25 baseline 채점 — ✅ 완료 (`eval/run_baseline.py`, 순수 파이썬·키 0)
4. 임베딩/하이브리드 — 🔄 진행 중 (`eval/run_embed.py`, Gemini 768-dim)
5. 이후 가점 / LLM grading을 얹으며 **하드필터 vs 가점** 등 비교

### 첫 성능 숫자 — BM25 baseline (2026-09-08)

```
Recall@1  = 0.667  (8/12)
Recall@5  = 0.833  (10/12)
Recall@10 = 0.833  (10/12)
MRR       = 0.741
```

- **8/12 1위 정답.** 변별 가능한 항목(스마트키·쇼핑백·크로스백·소설)은 완벽.
- **탈락 2건 = 같은 원인**: 한글↔영문 브랜드 동의어를 어휘 검색이 못 이음.
  - `닥스 검정 남성 지갑` → 89위 (정답 `DAKS 지갑`; "닥스"≠"DAKS", 남는 건 흔한 "검정 남성 지갑")
  - `아이코스 전자담배` → 21위 (정답 `IQOS 전자담배`)
  - 반대로 `엘지→LG`, `게스→GUESS`는 변별 토큰(노트북·에코)이 살려서 1위 성공.
- **의미**: 이 실패 패턴이 임베딩 도입을 정당화. **넘어야 할 하드 넘버 = MRR 0.741.**

### 임베딩 vs BM25 vs 하이브리드 (2026-09-08, 골든셋 v1 = 29문항 / 901건)

골든셋을 12→29로 확장(브랜드·영한 의미매칭·모델 정확·오타·약어 synonym·애매 유형 혼합).
같은 901건 코퍼스에서 세 방식 비교(BM25는 char-bigram 근사; 표 내부는 공정):

```
        BM25    EMB    HYB(0.5:0.5)
R@1    0.621  0.931  0.759
R@5    0.931  1.000  0.966
R@10   0.966  1.000  0.966
MRR    0.745  0.960  0.847
```

가중치 스윕(alpha=BM25 비율): **최적 alpha=0.0(순수 EMB), MRR 0.960**. BM25 비중이 커질수록 단조 하락.

- **강한 신호**: 이 도메인에서 **의미 임베딩이 주력 랭커**. 정확매칭·모델·오타·약어까지 커버,
  29문항 전부 top-5(R@5=1.000), 27/29 1위.
- **⚠ 하이브리드 반반은 손해**: HYB(0.5:0.5) 0.847 < EMB 0.960 → **융합 가중치는 튜닝 대상**(무비판 반반 금지).
- **⚠ 아직 "BM25 폐기" 근거는 아님** (정직한 한계):
  1. 우리 BM25는 **char-bigram 근사**지 실제 **nori BM25가 아님** → 실제 격차는 더 좁을 수 있음.
  2. 골든셋이 전부 "구별되는 정답이 코퍼스에 존재"하는 recall 테스트. **애매 질의 / 정답없음 /
     근접변형 구별**(A17 vs A15) 등 BM25가 값을 하는 유형 미포함.
- **실무 결론**: 임베딩 주력 + BM25 낮은 가중치 유지(하이브리드 폐기 X). 최적 배합은 nori 실측 + 어려운
  질의 확보 후 재판정. → **ADR 후보** (검색 랭킹 전략).
- 참고(v0, 12문항/892건): EMB MRR 0.958, HYB 0.922 — v1과 동일 경향.

### 실제 OpenSearch 실측 (2026-09-08, nori BM25 vs KNN vs HYB, 901건/29문항)

OpenSearch 2.17.1 + nori + k-NN(lucene HNSW cosine) 기동 → 901건 색인 → 실측:

```
        nori-BM25   KNN     HYB(0.5)
R@1      0.517     0.931    0.759
R@5      0.793     1.000    0.897
MRR      0.633     0.960    0.821
```
스윕 최적 = **KNN 100%, MRR 0.960**. BM25 비중↑ 단조 하락.

- **caveat #1 해소(측정으로)**: "nori면 BM25가 나아질 것"이라는 예상은 **반증됨**. 실제 nori BM25(0.633)가
  char-bigram 근사(0.745)보다 오히려 낮음 — 형태소 분해가 브랜드/고유명사(DAKS·CK 등)엔 불리
  (예: q16 캘빈클라인 CK, bigram 3위 → nori 50위). **실제 스택에서도 임베딩 압승 확정.**
- KNN은 오프라인과 동일(0.960) — 임베딩 결과가 실인덱스로 그대로 전이됨.
- 남은 단서: (a) naive multi_match라 nori BM25 천장은 아님(튜닝 여지 있으나 임베딩이 R@5=1.0이라 상한 이득 작음),
  (b) BM25가 값을 하는 질의 유형(근접모델 구별·정답없음)은 골든셋 미포함 → BM25 잔존 이유.
- **인프라 마일스톤**: 오프라인 근사 → **실제 검색 파이프라인(nori BM25 + KNN 하이브리드) 실동작**.

### 검색 데모 + 설계 규칙 (2026-09-08)

캐시된 골든 질의로 실검색 시연(Gemini 호출 0). 뜻검색이 실제로 작동:
- "닥스 검정 반지갑" → `DAKS검정반지갑`/`DAKS 지갑` 상위 (한글↔영문)
- "기업은행 대한항공 스카이패스" → `기업은행카드 (KOREAN AIR SKYPASS)` 1위 (영↔한 번역 매칭)
- "라도 손목시계" → `RADO 손목시계` 1위 / "로데 케이스 낀 핑크 아이폰" → `아이폰 (rhode 케이스)` 1위 (오타)

**⭐ 설계 규칙 (HNSW 근사 KNN)**: 보여줄 개수만큼만 `k`를 잡으면 진짜 정답도 누락될 수 있음.
- 실측: q04(아이코스) → k=6이면 정답 누락, k=50/300이면 1위.
- 규칙: **후보를 넉넉히(예: k≥100) 뽑고 → 상위 N개만 표시.** (search_demo 기본값 candidates=100 반영)

### ⭐ 가점(boosting) 실험 — 특히 "지역" (2026-09-14)

**동기**: 기존 골든셋 29문항은 브랜드 토큰이 뚜렷해 EMB만으로 R@5=1.000 → 가점 효과를 측정할
headroom이 없음. 가점의 진짜 가치(= 비슷한 것 수백 개 중 장소·시간으로 tie-break)를 재려면
**밀집 군집에서 일부러 묻히는 hard 케이스**가 필요. 그래서 hard 골든셋을 신설.

**산출물**
- `eval/data/police_stations_addr.csv` — 경찰청_전국 지구대 파출소 주소 현황(data.go.kr **파일데이터**, 로그인/키 불필요, cp949).
- `eval/build_gazetteer.py` → `eval/data/dep_gazetteer.json` — `dep`(보관장소) → 구/시 매핑.
  3단계 폴백(지구대·파출소 exact → 경찰서 컬럼 최빈 region → 지역토큰). **커버리지: 고유 dep 91% / 항목 74%.**
  남은 26% miss = 비경찰 포털기관(버스회사·지하철운영사·CGV·백화점) → 향후 별도.
- `eval/golden/golden_hard.json` — generic 질의(브랜드 토큰 X) 7문항. 검정지갑 193군집 등에서 정답이 EMB로 7~24위에 묻힘.
- `eval/run_boost.py` — EMB 코사인 위에 지역/시간/카테고리/색상 가점(soft, add/mult 모드) + 가중치 스윕.

**실측 결과 (오프라인, 코퍼스 2000 / hard 7문항)**

지역 가점(덧셈 w=0.15)만으로:
```
        R@1    R@3    R@5    MRR
EMB만  0.000  0.000  0.000  0.084   (7~24위에 묻힘)
+지역  0.714  1.000  1.000  0.857   (top-3 100%, 5/7 1위)
```

흐림(muddying) 스트레스 — **브랜드 질의 29개에 "틀린 지역"을 줬을 때** MRR(기준 0.940):
```
w_region  0.00→0.940  0.05→0.871  0.10→0.741  0.15→0.604  0.30→0.019
```

덧셈 vs 곱셈(각자 hard 회복시키는 가중치에서 안전성):
```
mode  w     hardMRR  brandWrongMRR
add   0.05   0.857     0.871    ← 채택
mult  0.15   0.857     0.703
```

**결론 (ADR 후보: 검색 랭킹 — 지역 가점)**
1. **지역 가점은 강력**: 묻힌 정답을 MRR 0.084 → 0.857. 밀집 군집 tie-break의 핵심.
2. **덧셈 소프트, 작은 가중치(~0.05)**: hard셋 완전 회복 + 지역 추측이 *틀려도* 브랜드 손실 -0.07로 억제.
   과가점(w≥0.15)은 틀린 추측 시 좋은 검색을 파괴 → 금지. (곱셈 가설은 eval로 반증됨.)
3. **하드필터가 아니라 가점인 이유 실증**: 지역을 틀리게 잡아도 정답은 아래로 밀릴 뿐 사라지지 않음
   (필터면 0건). **순천→광주 지갑**을 안 놓침. "노선 도우미로 지역집합을 넓게"가 이 위험을 줄이는 장치.
4. 시간·카테고리·색상은 이 hard셋에선 델타 0(지역이 이미 top-3 채움) → **이 테스트에선 보류**,
   근접모델 구별/정답없음 케이스에서 재검증 대상.

**장소 가점 설계 원칙(사용자 확정)**: 분실지≠보관지. 물건은 교통노선 방향으로 이동해 종점 근처에 보관됨.
→ 장소 가점 = 후보 `dep`의 구/시가 **"노선 경유 구역 집합"**에 드는가. 넓게(최소 구 단위). 노선 추론은
자동 점수가 아니라 **사용자가 지역집합을 정할 때 돕는 HITL 도우미**로(부산역 기차 → 경유 구역 제안 → 사용자 확정).

**남은 일**: tie-aware 게이트(상위 후보가 애매할 때만 가점 발동)로 흐림을 원천 차단 / 근접모델·정답없음 hard 케이스 추가.

### 지역 커버리지 확장 — 짧은이름 substring + 지오코딩 API (2026-09-14)

**정적 vs API 원칙**: 안 바뀌는 경찰관서 매핑은 CSV→로컬표(런타임 호출 X). API는 (a) CSV가 못 덮는 것,
(b) 실시간 노선 경유지(노선 도우미)에만.

1. **무료 개선(키 X)**: gazetteer에 도시/구 짧은이름(`부산`,`익산`,`광진`…) substring 폴백 추가(괄호 안 포함).
   `다이소(부산당리점)`→부산, `광주청년센터`→광주 식으로 잡아 **항목 커버리지 74%→86%** (`build_gazetteer.py`).
2. **지오코딩 API(키 필요, `eval/geocode_deps.py`)**: 남은 14%(역·랜드마크·상호: `올리브영(홍대입구역점)`,
   `해운대해수욕장`, `삼성여객자동차`)를 **카카오 로컬 키워드검색**으로 구/시 해석.
   - 설계: **빌드타임 1회 보강** → `eval/data/dep_geocoded.json` 캐시 → 런타임 로컬 조회(정적 원칙 유지).
   - **key-gated**: `.env`의 `KAKAO_REST_API_KEY` 없으면 안내 후 종료(크래시 X). 실패도 ""로 캐시해 재호출 방지.
   - `--selftest`로 주소 파싱 오프라인 검증(PASS). 해석기(run_boost `make_resolver`)가 캐시를 최후 폴백으로 참조.
   - **활성화**: developers.kakao.com 앱에서 **카카오맵(Local) 서비스 ON** + 무료 REST 키 → `.env`
     `KAKAO_REST_API_KEY` → `python eval/geocode_deps.py`. (앱 카카오맵 OFF면 403 NotAuthorizedError.)
   - 검색어: 브랜드+지점 구체검색 먼저 → 없으면 지점명만 폴백(동명이지 오매칭 방지: `포토이즘(서면점)`→부산 부산진구).
     원칙: **틀린 지역보다 무(無)지역**(틀리면 잘못 가점, 없으면 가점 안 함).
   - **실측(2026-09-15): 미해석 25건 중 20건 해석 → 커버리지 86%→95%.** 남은 5건은 해외(주고베총영사관)·
     시설꼬리(롯데백화점 일산점 안전실) 등. 상호명 매칭(삼성여객→서초 등)은 저신뢰지만 soft boost라 안전(하드필터 아님).
   - 참고: 미해석 dep은 전부 포털기관(V-src)이라 현 골든/hard 정답(경찰 항목)엔 영향 없음 → 프로덕션 커버리지용.
3. **노선 경유지 API**: 당신의 "노선 도우미"(부산역 기차→경유 구역 제안, HITL)는 서울버스/철도 노선 API
   (서울버스는 사용자 계정 승인됨). 이건 자동 점수 아닌 지역집합 설정 보조 → agent/app 단계에서.

### LLM grading — 검색 top-K 재정렬 (2026-09-15)

**설계**: EMB top-K(기본 10)를 `gemini-3.6-flash`가 0~100 채점(+한줄 근거) → 재정렬. LLM은 DB 아닌 심판
(K개만 판정, 전체 코퍼스 프롬프트 금지). 채점은 `eval/data/grade_cache.json`에 질의별 캐시(재실행 오프라인).
산출물: `eval/run_grade.py`, 프롬프트는 스크립트 내 `PROMPT`(앱 단계에서 `apps/agent/prompts/`로 이동 예정).

**⚠ 모델 주의**: `gemini-2.5-flash`는 이 계정/시점에 신규차단(404 "no longer available to new users") →
**`gemini-3.6-flash` 사용**. `responseMimeType: application/json` + temperature 0으로 JSON 강제.

**실측 (29 골든, K=10)**
```
        R@1    R@3    R@5    MRR
EMB    0.897  0.966  1.000  0.940
GRADE  0.897  1.000  1.000  0.943   (q13 프라다 4→3위, 악화 0건)
```

**해석 (정직)**
- 랭킹 이득 작음: EMB가 이미 0.940 천장이라 예상된 결과. brand 질의는 임베딩이 거의 다 맞힘.
- grading의 값은 MRR에 안 잡히는 곳: (1) **근거 설명**(제품 핵심 — "rhode=로데 케이스 핑크까지 일치"),
  (2) **신뢰도 점수**로 "정답 없음" 필터/임계값, (3) **라벨 검증**.
- **골든 라벨 오류 발견**: q01 정답라벨 `DAKS 지갑`(82점)보다 grading 1위 `DAKS검정반지갑`(98점)이 질의
  "닥스 검정 남성 반지갑"에 더 정확 → 골든셋 라벨 재검토 필요(grading이 라벨 품질까지 검증).
- **남은 검증**: "정답 없음"(코퍼스에 없는 물건) 케이스에서 grading이 전부 저점 주는지 → EMB 불가능한 필터링 가치 실증.

**결정: 코사인 임계값은 도입 안 함 (측정 후 폐기, 2026-09-15)**
- 정답 코사인 [0.758~0.950] vs 최선오답 코사인 [0.572~0.942] → **분포 거의 완전 겹침.** 오답이 정답보다
  높은 경우도 있음(q07 0.942>0.898, q13 0.937>0.884, q01 0.837>0.826).
- "모든 정답 통과" T=0.758이면 오답 19/29 통과, "모든 오답 차단" T=0.942면 정답 26/29 탈락 → **단일 임계값 불가.**
- 쓰레기 1차 컷 용도도 무의미(이미 top-K만 grading→top-10은 대부분 0.6↑). "정답없음" 감지도 실패(generic 오답 0.94).
- **의미 있는 임계값은 코사인이 아니라 LLM grade 점수(0~100)에 건다** — grade는 보정된 "판단"이라 컷값이 성립.
  이 컷값은 향후 "정답없음" 테스트로 잡음.

### ⭐ 매칭 에이전트 (LangGraph) 린 v1 (2026-09-15)

**"부품 → 오케스트레이션"**: 검색·가점·grading·수집기를 에이전트가 엮어 *자연어 신고 한 줄 → 매칭*.

**구조** `apps/agent/` (LangGraph StateGraph, 노드는 평범한 함수):
```
extract → route → fanout → search(병합) → grade
```
- `extract.py` — 신고 자연어 → {item,brand,color,category,place_context,lost_date,features}. 상대날짜("어제")를 오늘 기준 환산.
- `route.py` — **RouteResolver 인터페이스** + LLM지식 스텁. 장소맥락 → 경유 구/시 집합. **노선 API 없이** 동작
  (Gemini가 "2호선 경유 구"를 나열). 추후 지하철/버스/기차 노선 API를 같은 인터페이스에 주입(에이전트 무변경).
- `fanout.py` — 구조화 → 넓게~좁게 쿼리(규칙기반): "닥스 검정 지갑"→"검정 지갑"→"지갑".
- `graph.py` — 각 쿼리를 검색+지역가점(기존 파이프라인) → atcId로 병합·dedup → merged top-K를 grading.
- 프롬프트는 `apps/agent/prompts/{extract,route}.txt` (파일 분리).

**API**: `POST /lost-items {text, lost_date?}` → 추출·지역집합·fan-out·매칭을 투명하게 반환.

**실동작**: "어제 2호선 지하철에서 검정 닥스 지갑..." →
- 추출: 닥스/검정/지갑, "어제"→2026-09-14, 장소=2호선 지하철.
- 지역집합: LLM이 2호선 경유 ~19개 구 나열(강남·서초·송파·성동·마포·강서...).
- 매칭: **DAKS검정반지갑 grade=95**(강서구=2호선 구간→지역가점까지), 일반 검정지갑 50~60으로 구별.

**남은 일(에이전트)**: DB 저장(PostgreSQL) + 신규 습득물 유입 시 **지속 재매칭** / grade 낮으면 fan-out 확장 재검색(분기·루프) /
RouteResolver를 실제 노선 API로 / HITL(지역집합 사용자 확인) / 알림 연결.

### ⭐ 분실물 DB + 지속 재매칭 (2026-09-15)

**"1회성 → 계속 지켜봄"**: 에이전트가 등록 즉시 매칭하고 끝나던 것을, 신고를 저장하고 새 습득물이
들어올 때마다 재매칭하도록. 분실물은 보통 나중에 발견됨 → 접수해두고 유입마다 대조하는 게 핵심.

**저장소** (린 v1: SQLite stdlib, 추후 PostgreSQL): `apps/store.py`, `data/findit.db`(개인정보 → gitignore).
lost_items(id, user_id, text, extracted, region_set, queries, status, best_match, best_grade, ...).

**흐름**:
- `POST /lost-items` — 에이전트 매칭 + **저장**. 최고 grade ≥ 임계(기본 80)면 status=matched, 아니면 open.
- `apps/agent/rematch.py` — open 항목을 현재 인덱스와 재매칭. 저장된 추출·지역집합·쿼리 재사용
  (`graph.match_stored`: LLM 추출/라우팅 재호출 없이 검색+grade만 → 저렴). 임계 넘으면 matched + 알림 대상 반환.
- `수집기 --rematch` — 색인 후 자동으로 `rematch_open()` 호출(수집→재매칭 루프).
- 조회: `GET /lost-items`, `GET /lost-items/{id}`.

**실동작(통제 시연)**: 애플워치를 인덱스에서 삭제 → "애플워치 잃어버렸어요" 신고 = **open(grade 65)** →
수집기가 애플워치 재색인 `--rematch` → **자동 matched(grade 80, "알림 대상")**. 페라리 미니카(코퍼스에 없음)는 open 유지.
→ **등록 시 없던 매칭이 습득물 유입 후 자동 성립**. 알림(Notifier)과 연결될 seam("알림 대상") 확보.

**남은 일**: 알림(Notifier→콘솔→카카오) 연결 / 중복 알림 방지·이력 / PostgreSQL 이전 / user_id(인증) /
쿼리 임베딩 캐시로 재매칭 더 저렴하게 / 스케줄러가 수집→재매칭 정기 실행.

### 알림(Notifier) — 채널 독립 (2026-09-15)

헌장대로 **알림은 인터페이스로만**. `apps/notifier.py`: `Notifier` Protocol + `ConsoleNotifier`(v1 로그).
주입 지점 `notifier` — 추후 KakaoNotifier 등으로 교체(코어 무변경). 공식 신고 제출은 별도 HITL(여기선 통보만).

**연결**: 매칭 성립(matched 전환) 지점 두 곳에서 `notifier.notify(lost, match)` —
(1) `POST /lost-items` 등록 즉시 매칭, (2) `rematch_open()` 재매칭 성립. 중복 방지는 status 전환으로
자연 처리(matched는 open 풀에서 빠져 재알림 없음).

**실동작**: "라도 손목시계" 등록 → matched(95) → `🔔 [알림→anon] ... RADO 손목시계, 보관:정관아쿠아드림파크, 부산 기장군`.

**채널**: `console`(기본) / `email`(SMTP). `NOTIFIER_CHANNEL`로 선택, `get_notifier()` 팩토리. 미설정 시 console 폴백.
- `EmailNotifier`(SMTP, Gmail 앱 비밀번호): matched 시 수신자에게 메일. 발송 실패해도 요청 안 죽음(로그 후 진행).
- **카카오 알림톡은 사업자등록증(개인사업자 포함) 필수** → 비사업자는 불가. "나에게 보내기"는 나와의 채팅 침범이라 데모 부적합
  → **이메일 채널 채택**. (알림톡은 사업자 확보 후 발송대행 API를 같은 Notifier 인터페이스로 추가.)

**수신자 = 신고자별 이메일**(등록 시 입력·저장, 고정 아님). 보내는 SMTP 계정만 서비스 하나로 고정.
**라이브 발송 확인됨**(실제 메일 수신). Notifier.notify(lost, **matches 리스트**)로 변경 —
최고 매칭 + **비슷한 후보 목록**(상위 5) 함께 발송. **HTML 메일 + 썸네일**(image_url 실제 URL만,
경찰청 no_img 플레이스홀더는 숨김). 텍스트/HTML 멀티파트.

**남은 일**: 알림 이력·중복 방지 / 연락처(orgNm·tel) 포함 / (사업자 확보 시) 알림톡을 같은 Notifier로.

### ⭐ HITL 확인/수령 흐름 — "매칭됨" 자동확정 제거 (2026-09-18)

**문제 제기(사용자)**: grade≥80을 자동 "매칭됨(확정)"으로 단정하면 안 됨 — LLM grade는 신뢰도 추정이지
증명이 아니고, 실제 "내 물건" 확인·수령은 사용자만 가능. 헌장의 HITL 원칙과도 어긋남.

**개선**: 시스템은 **유력 후보 제시**까지, 사용자가 **확인**.
```
open(찾는중) → [grade≥80] → candidate(유력 후보, 알림) → 사용자:
                                    ├ '내 물건이에요' → confirmed(+수령 안내)
                                    └ '아니에요'      → open(그 후보 dismissed 제외하고 계속)
```
- 상태 `matched`(자동확정) 제거 → `candidate`/`confirmed`. store에 `dismissed`(atc_id 리스트) 추가.
- API: `POST /lost-items/{id}/confirm`(match) · `/dismiss`(atc_id). rematch는 dismissed 제외.
- 웹: 후보 카드에 [내 물건이에요]/[아니에요] 버튼. 확인 시 **수령 안내**(보관기관·☎연락처·lost112 링크).
- 알림 문구: "매칭됐어요" → "유력 후보를 찾았어요, 확인해보세요" + 보관기관·연락처·lost112.
- **경계(HITL)**: 시스템은 안내까지만, 전화·수령·공식신고는 사용자. 자동으로 남의 물건을 "네 것"이라 단정 X.
- 수령 정보(org_name·tel)는 [FIND-18]에서 수집기가 색인(임베딩 미포함, 표시용).

### ⭐ 이미지 레인 — 사진으로 분실물 찾기 (Gemini Vision) (2026-09-19)

**설계 1-3 재확인**: 멀티모달 임베딩 학습 없이 **"특징 텍스트화"가 주력**. 사진을 벡터로 직접 매칭하지 않고,
Vision으로 **텍스트 필드를 추출**해 **기존 텍스트 파이프라인을 그대로 재사용** — 레인 추가에 검색·가점·grade 로직 무변경.

**왜 image-to-image(CLIP) 안 쓰나 — 데이터 기반 결정**: 라이브 색인 표본 실측 결과 **습득물의 ~22%만
유효 사진 보유**(나머지 78%는 `no_img` 플레이스홀더). 이미지 임베딩으로만 매칭하면 데이터의 78%를 못 봄.
그래서 사진→특징 텍스트화→텍스트 검색이 **100% 데이터에 동작하는 현실적 최적**.

**+ VISUAL 레인 (2026-09-20, C안 채택)**: "진짜 사진 비교"를 두 방식으로 검토 —
- **A. 이미지 임베딩(CLIP) 전체 KNN**: 텍스트 무관 시각 검색(놓친 것도 발견) but torch+모델 도입 →
  8GB VPS RAM 압박(OOM)·전날 대공사 리스크. (OpenSearch 용량은 무관: 512-dim 벡터 1,300건 ~2.6MB.) → **심사 후 확장.**
- **C. Gemini 사진 대조(채택)**: 텍스트로 추린 후보 중 **사진 있는 상위 3개**를 [사용자 사진 + 후보 사진]
  멀티모달로 직접 비교 → `visual_score`(0~100)+근거. **새 모델·색인·의존성 0**(RAM 무관), 실패는 스킵.
  실측: 로고(그래픽) 입력 시 실제 폰 사진과 visual=0으로 **정확히 판별**(도장 아님). 사진 없는 후보(≈78%)는
  텍스트로만 → **텍스트+비주얼 두 방향 공존**. (한계: 후보당 fetch+1콜이라 +몇 초, 사진 있는 후보만.)

- **흐름**: 사진(+선택 메모) → `gemini.generate_json_image`(멀티모달 generateContent, inline_data) →
  `extract_image`가 텍스트 추출과 **동일 필드 스키마**(item/brand/color/category/features) 반환 →
  `graph.run_image`가 추출 필드로 검색용 text 합성 → **route→fanout→search→grade** 재사용 → 저장·알림·HITL 공유.
- **경계 설계**: 사진은 **장소·날짜를 모름** → `place_context`/`lost_date`는 사용자 메모/분실일에서만 채움(추측 금지).
  즉 사진=물건 특징, 메모=맥락. 두 신호를 각자 잘하는 데서만 취함.
- **업로드**: 멀티파트 의존성(`python-multipart`) 추가 없이 **base64 JSON**(`POST /lost-items/image`) — 사진 1장 규모라 충분.
- **웹**: '사진으로 찾기' 레인(파일선택+미리보기). 결과 렌더 공용화(`renderResult`)로 텍스트/사진 동일 UI.
  결과에 **올린 사진 + Vision이 읽은 내용**을 노출 → "AI가 내 사진을 어떻게 이해했나" 투명성(HITL 신뢰).
- **실측(라이브)**: 로고(파란 폰 일러스트) 입력 → Vision "스마트폰/파란색", 메모 "2호선"→지역집합 16구 →
  후보 12건 1위 **grade 85 삼성폰(블루)**. Vision→검색→판정→저장 전 과정 프로덕션 동작 확인.

### ⭐ 전체 둘러보기(목록+필터) + 결과 이메일 + region 색인화 (2026-09-20)

**동기(사용자)**: AI 매칭만이 아니라 **① 전체 습득물을 한눈에 보는 목록**(키워드·지역·날짜 필터) +
② AI 에이전트 검색 + ③ 알림, 3-사이트 구성. 심사자가 "데이터가 실제로 쌓여있다"를 즉시 확인.

- **둘러보기 검색**: `GET /found-items/browse` — BM25 키워드 + 지역/날짜 필터 + 최신순 + 페이지네이션 +
  `region` terms 집계로 지역 드롭다운(건수 포함). **임베딩·LLM 미사용 → 무료·즉시**(브라우징엔 의미검색 불필요).
- **region 색인화**: 기존엔 검색 때 실시간 해석뿐이라 필터/집계 불가 → 매핑에 `region`(keyword) 추가,
  수집기가 색인 시 채움. 기존 문서는 2단 백필: (1) `backfill_region.py`(정적 gazetteer, 비용 0, 4,893건),
  (2) `geocode_region.py`(미커버 dep만 카카오 지오코딩, 무료, 고유 dep 54종→46종 해결·850건). 커버리지 ~85%+.
- **결과 이메일**: 이메일 미입력으로 검색 시 결과창에 "이메일 남기면 결과 보내고 이후 매칭도 알림" +
  입력칸·[보내기] → `POST /lost-items/{id}/email`(사용자 본인이 직접 트리거, `store.set_email`로 이후 알림도 그 주소).
- **사진 안내(정직)**: 사진 선택 아래 "습득물은 사진이 없는 경우가 많음, 사진끼리 비교가 아니라 특징을 텍스트화해
  검색" 명시 — 한계를 숨기지 않고 기대치를 맞춤.
- **웹**: 상단 탭 `[🔍 AI로 찾기 | 📋 전체 둘러보기]`. 라이브 확인: 총 5,940건, 강남구 필터 323건, 지구대/파출소까지 지역 표시.

> 설계 메모: **장소 구조화 UI(교통수단→노선→역→방향)는 보류**. 소프트 가점(w=0.05) 하나 위해 정교한
> 셀렉터는 가성비 낮음(색·종류가 다르면 장소로 못 뒤집음). 버스 노선→구는 API 필요(무겁다) → 심사 후로.
> **경로 가점은 "전 지역 검색 + 경로 구 가점"**(하드필터 아님) — KTX 서울→부산이면 경로 구 모두 가점 대상.

### ⭐⭐ 외국인 접근성 — 다국어(EN/KO) + 영어 수령안내·경로설명·판정근거 (2026-09-20)

**차별화의 핵심**: 관공서(경찰민원24·lost112)는 **전부 한국어 → 외국인은 사실상 못 씀.** 신고·알림 등 다른
기능은 관공서와 겹치지만, **외국인 접근성은 언어장벽 때문에 관공서가 구조적으로 못 하는 유일한 지점.**

- **검색은 언어 무관**(실측): 영어 입력 *"I lost my black leather wallet on Seoul subway line 2"* →
  extract가 한국어 필드로 정규화(지갑·검정·서울 지하철 2호선) → 임베딩 한↔영 → grade 85 "검은색 지갑" 발견.

  `/lost-items`·`/lost-items/image`에 `lang`, graph.run/run_image 관통. 항목 데이터는 한국어 원문 유지(번역 비용 회피).
- **웹 i18n**: EN/KO 토글(localStorage) + 사전 + `t()` + `applyLang()`(data-i18n 태그). 검색·둘러보기·결과·목록 전환.
- **외국인 특화 안내**(핵심 가치):
  - **영어 수령 방법**: 전화 → 여권/신분증 지참 방문(본인확인) → 지도 → lost112 → 보관기간(최대 6개월) 안내.
    (사용자가 공유한 경찰민원24 실제 절차와 일치)
  - **🗺 지도 링크**: 보관기관을 Google Maps로(외국인 자기 언어 길찾기).
  - **경로 설명 영어판**: "외국인은 그 노선이 어디까지 가는지 모른다" → *"You may not know where that line goes —
    so we searched every district it passes through and boosted them (we don't filter)."* 노선 기반 가점 로직을 설명으로 노출.
- 라이브 검증: EN 토글 → 영어 질의 → 경로설명·판정근거·지도·수령안내 모두 영어로 정상 렌더.

> 포지셔닝 결론: FindIt = **"관공서 공개데이터 위에, (1) 더 똑똑한 검색 + (2) 외국인 접근성을 얹은 레이어."**
> 신고·알림·수령은 관공서와 겹치는 table-stakes, **차별점은 '검색 품질'과 '외국인 접근성' 둘.**

### 약한 후보 알림 — 신고별 옵트인 + 하한선 (2026-09-29)

- **신고별 옵트인**: 웹 체크박스 "정확도가 낮은 비슷한 후보도 참고로 알림 받기"(등록 폼 + 결과창 이메일 패널). 기본 꺼짐 → 기존 동작 유지.

### ⭐ 다국어 알림 메일 — 신고자 언어로 발송 (2026-09-30)

**문제(사용자 지적)**: 화면은 Google 번역 위젯이 번역하지만 서버엔 항상 `lang: "ko"`가 전달돼, **알림 메일·재매칭 판정 근거가 무조건 한국어**.
외국인 관광객이 핵심인 서비스에서 모순.

- **사용자 언어 결정(웹 `userLang`)**: ① 번역 위젯에서 고른 언어(googtrans 쿠키) ② 입력에 한글이 있으면 ko ③ 그 외 브라우저 언어.

- **신고에 `lang` 저장**(컬럼 자동 마이그레이션) → 등록 알림뿐 아니라 **재매칭 판정 근거·알림도 신고 언어**(`match_stored(lang=)`).
  판정 언어 지원을 4개(영·일·중·한) → **위젯 13개 언어 + 한국어**로 확장(그 외 코드는 코드명 그대로 지시).
- **메일 번역**: 고정 문구를 문구 사전(`KO`)으로 모으고 언어별로 **한 번 번역해 캐시**, 물품·분류·장소는 **메일마다 1회 번역**.

  물품명·설명은 판정 단계가 이미 사용자 언어로 만든 값을 우선 사용. 자리표시자(`{t}` 등)가 깨진 번역은 거부.
  **폴백**: 해당 언어 실패 → 영어 → 한국어(메일이 안 가는 일은 없음). 한국어 사용자는 번역 호출 0(기존과 동일).
- 실측(실제 Gemini): 일본어·베트남어 메일 제목·문구·물품·장소 모두 자연스럽게 번역, 자리표시자 잔존 0.
- 테스트: `tests/test_i18n_email.py`(언어 정리 11케이스, 한국어 무번역, 외국어 번역·name_en 우선·장소 원문 유지,

### ✅ (해결) 반복 병목: Gemini 무료 임베딩 쿼터 (개발 루프 차단)

- 개발 초기 임베딩 대량/자유질의 시 **5회 이상 429 RESOURCE_EXHAUSTED**. 소량 버스트만 허용, 회복에 10~15분.
- 캐시된 골든셋 eval/데모는 되지만, **새 자유질의는 즉석 임베딩 필요 → 매번 막힘**. 프로덕션에서도 문제.
- **결정: (b) Gemini 유료(종량제) 활성화** → rate limit 해소. 비용은 임베딩 하루 수 센트 수준(수집 ~2,800건/일 기준).

### Gemini 무료 티어 임베딩 쿼터 (실측 주의)

- 소량 버스트만 허용 → 대량 배치 시 429 RESOURCE_EXHAUSTED, **약 10~15분 쿨다운 후 회복**(하드 일일캡 아님).
- 대응: 질의/코퍼스 임베딩은 **디스크 캐시**(`eval/data/emb_cache.json`, 질의는 `q::<id>` 키) + 소배치 +
  우아한 degrade(캐시된 것만으로 평가). 반복 eval에는 로컬 임베딩 모델 검토 여지.

### 임베딩 모델 확인 (Gemini)

- 사용 가능: `gemini-embedding-001`(선택), `gemini-embedding-2(-preview)`.

## 8. 아키텍처 원칙 (위반 금지 — 프로젝트 헌장)

- **채널 독립 코어**: 비즈니스 로직에 카카오/웹 의존성 금지. 알림은 `Notifier` 인터페이스로만.
- 사용자 식별은 내부 `user.id`. `kakao_id`를 FK로 쓰지 않음.
- **장소·시간은 가점, 하드필터 금지.**
- 되돌릴 수 없는 액션(공식 신고 제출)은 자동화 금지 — **HITL(사용자 승인) 유지.**
- LLM 호출은 목적별 함수로 분리 — 현재 `apps/api/gemini.py`(embed_query·embed_texts·generate_json·generate_json_image·compare_images·grade).
  프롬프트는 `apps/agent/prompts/`에 파일로(extract·extract_image·route). ※ grade 프롬프트는 아직 `gemini.py` 안에 있음(파일 분리 대상).
- 공공 API 필드는 **`fixtures/responses/` 샘플이 진실.** 추측으로 필드명 만들지 않음.
- OpenSearch 매핑 변경 시 `infra/opensearch/mappings/` JSON도 반드시 갱신.
- 큰 작업은 구현 전 계획 제시·승인.
